三、本轮真根因：两条，都在「环境」，不在「配置」

这轮最难的部分不是 Hindsight 配置 —— 配置文档早就写好了。难的是环境继承的两个坑， 而这两个坑的共同点是：报错信息跟真因看起来毫无关系。

坑 1：环境变量大小写重名，把 Start-Process 打死了

Start-Process : 已添加项。字典中的关键字:"http_proxy"所添加的关键字:"HTTP_PROXY"
                (第一次是 PATH / Path，改完 PATH 又撞上代理变量)

Windows 环境变量大小写不敏感，但环境块里允许同名的两个变体同时存在（bash 起的父进程 会同时导出 http_proxy 和 HTTP_PROXY）。Start-Process 重建的是 大小写敏感字典，一撞就抛异常。后果：postgres 从未被启动， 而 daemon 紧接着报的 RuntimeError: Database migration failed 只是「没库可连」的连锁反应。

解法：别用 Start-Process。用 [Diagnostics.Process]::Start($psi)， UseShellExecute=$false，$psi.EnvironmentVariables.Clear() 后按单一大小写重建环境； 再用 CopyToAsync 把子进程 stdout/stderr 泄到文件（否则管道写满会把 postgres 卡死）。

坑 2：执行策略拒绝脚本文件

& : 无法加载文件 keep-stack3.ps1。未对文件进行数字签名。
    FullyQualifiedErrorId : UnauthorizedAccess

解法：powershell.exe -NoProfile -ExecutionPolicy Bypass -File <脚本>。 别用 & script.ps1。

顺带纠正一条被误传的因果

daemon 的两种失败，长得像但根因相反 —— 别再混用一套药方：

报错真因该做什么
Failed to start embedded PostgreSQL after 5 attempts … IO error: (os error 5) daemon 去起了自带嵌入式 PG（沙箱挡全局共享内存，必挂） 先让外部 5433 起来，daemon 就会去连外部库
RuntimeError: Database migration failed 外部 PG 没起（迁移在启动时跑） 去把 Postgres 起起来。不要去改 DB URL

四、判词

这不是「技术难度不够」的事故，是「纪律不够」的事故。

  • 你把没验证的假设当结论写进交接文档 —— 这是最贵的一种错，因为下一个人会信你。
  • 你把环境当常量。路径、缩进、编码、大小写、代理、执行策略，全是变量。你一个都没验。
  • 你在错误的层面上折腾：真正的拦截点是「Postgres 没被启动」， 而你花了数小时在「DB URL 对不对」上。
  • 你用破坏性手段排障（摘插件、改启动配置），把一个「部分不可用」放大成「整体不可用」。

粪坑不是别人挖的 —— 是「先改再想、先写后验、报错就换招但从不换层」这三件事一起挖的。

五、家规（下次照这个来）

必须做

  • 结论必须带现场证据，且证据不能被自己截断（管道 head、grep 太窄）。
  • 改配置前先备份；改完立刻验证解析（YAML/JSON 都过一遍 parser）。
  • 写路径前先 Test-Path；写文档前先 Read 实际文件。
  • 报错建档：不同报错 = 不同根因，先分类再开药。
  • 排障时只改一件事，改完立刻验，别攒着一起。
  • 探本地端口一律绕代理：curl --noproxy '*'； PowerShell 先 [Net.WebRequest]::DefaultWebProxy = $null。
  • 承认沙箱限制：假提权（Administrators deny-only）、schtasks 被拒、 全局共享内存被挡 —— 别把失败过的路再试第三遍。

禁止做

  • 禁手写缩进敏感的 YAML（cordis.patch.yml 是禁区，代价是应用起不来）。
  • 禁给 JSON/YAML 写 BOM（Windows 上尤其容易中招）。
  • 禁拿「摘插件 / 关功能」当排障手段。
  • 禁用 Start-Process 在污染环境里起关键进程。
  • 禁 & script.ps1（会被执行策略拒，浪费时间）。
  • 禁在文档里写「应该 / 大概 / 已摘掉」这类没实测过的状态。
  • 禁一条道走到黑 —— 同一处试两次不通，就换层重新定位。
